# Product Scope —— 需求收敛与 MVP 范围裁剪

> 场景：非技术用户说「我想做一个 XX 应用」。本 skill 是接单后的第一道闸门——先收敛范围，再谈技术实现。
> 原则：「听起来有用」不构成进 MVP 的理由；任何不参与验证核心假设的功能，进 backlog 不进 v1（R4-B2）。

## 何时使用

1. 用户提出一个全新的「做一个 XX 应用/平台/系统」需求，尚未有明确功能清单；
2. 用户给出一份长长的功能愿望单，需要判断哪些进第一版；
3. 项目进行中途，用户临时追加「顺便加个支付/通知/多语言」等能力；
4. 需求描述模糊到无法直接开工（没有目标用户、没有核心流程）；
5. 用户问「第一版应该做什么」「这些功能都要吗」。

## 规范做法

### 一、先锁定三件事，再谈功能（R4-B1）

在生成任何代码之前，先与用户确认并写下三句话：

1. **一个目标用户**：谁会用这个产品？具体到人群（如「独立化妆师」而非「爱美人士」）。
2. **一个痛苦工作流**：这个用户现在用 Excel/微信/纸笔凑合完成的、最痛的那个流程是什么？
3. **一个待验证假设**：如果第一版只能验证一件事，验证什么？（通常是「这个人群愿意为解决这个问题付出时间/金钱」。）

然后从这三件事**反推**「验证该假设所需的最少功能」。功能不是愿望单堆出来的，是假设推出来的（R4-B1）。

### 二、MVP 五件套（默认交付边界）（R4-B1）

第一版的标准交付就是这五件，不多不少：

| # | 部件 | 验收标准 |
|---|------|---------|
| 1 | Landing / 展示页 | 说清产品价值，带注册入口（可收集 waitlist），验证需求 |
| 2 | 注册登录 | 本栈为自建 session cookie 认证（见 security-baseline），密码 Argon2/bcrypt 哈希，能注册、登录、登出、改密码 |
| 3 | 单一核心 CRUD | **只做「那一个」**兑现核心价值的功能闭环（如预约应用的「预约单」），列表+新建+编辑+删除，分页带默认 limit |
| 4 | 响应式 UI | 移动端可用（不断版、可点按），不追求完美设计 |
| 5 | 部署上线 + 基础埋点 | 真实域名可访问；至少有「注册数/核心操作次数」级的事件记录（服务端日志或轻量埋点），能收到真实反馈才算 MVP 完成 |

「能做但是五件套之外」的功能，默认不做（R4-B1）。

### 三、需求澄清提问清单（动手前主动问）

需求模糊时，agent 应**主动向用户提出**以下问题，而不是自行脑补：

1. 这个产品是给谁用的？能描述一个最典型的用户和他的使用场景吗？
2. 他现在不用你的产品时，是怎么解决这个问题的？最烦的一步是什么？
3. 如果第一版只能做一件事，哪件事不做就「等于没做」？
4. 用户需要注册登录吗？数据是每人私有，还是公开/共享的？
5. 有没有必须在手机上用的场景？（决定响应式优先级）
6. 这次上线想验证什么——是「有人愿意注册」，还是「有人愿意付钱」？
7. 你提到想要 A/B/C 功能，它们和上面那件「必须做的事」是什么关系？能晚一点再加吗？
8. 有没有明确的时间/预算约束？（决定砍功能的狠度）

### 四、范围蔓延识别与拒绝话术（R4-B2）

以下四项是最高频的范围蔓延项。识别到用户提出时，**不要默默照做，也不要生硬拒绝**——先认可价值，再说明为什么第一版不做，并给出替代方案与「何时再加」的触发条件：

**1. 支付（Stripe 订阅/多档定价）**
> 话术模板：「支付接入本身不难，但税务、退款、Webhook 可靠性是长期负担。第一版建议先用『单一价格 + 手工开通』甚至先免费收用户，等验证出真实留存和付费意愿，再接 Stripe。多档定价同理——先用一个价格验证『有没有人付钱』，再谈分层。」（R4-B2）

**2. 实时协作（WebSocket/多人编辑）**
> 话术模板：「实时协作需要冲突解决、在线状态、CRDT 这类机制，复杂度是普通功能的十倍量级。第一版用『异步操作 + 刷新可见』就能覆盖绝大多数场景——MVP 阶段的真实用户量通常根本触发不了协作需求。等出现『多人同时改同一份数据』的真实抱怨时再升级。」（R4-B2）

**3. 通知中心（邮件/短信/站内信三件套）**
> 话术模板：「第一版只保留不可或缺的事务性邮件：注册确认和密码重置。营销邮件、短信、站内通知中心、通知偏好设置页全部延后——它们不参与验证核心假设。等有真实用户反馈『错过了重要事件』再按需补。」（R4-B2）

**4. Admin 后台与 i18n**
> 话术模板：「用户量不到 100 时，管理员操作直接用数据库表编辑器或 SQL 完成，不值得单独建 admin UI。多语言会污染所有文案代码路径，第一版锁定单一语言市场，验证通过后再国际化。这两项都进 backlog，不进 v1。」（R4-B2）

通用判断原则：任何「将来一定需要」但**不参与验证核心假设**的功能，记录进 backlog 并明确告知用户，不进 v1（R4-B2）。

### 五、技术选型态度：少做决策（R4-B1）

不与用户讨论技术选型菜单。本库已锁定技术栈（Go 后端 + React 或 Vue 前端 + Postgres + Docker Compose，详见 fullstack-architecture）。对用户只说结论：「每少一个自建组件就少一类上线事故，我们用一套经过验证的标准栈。」（R4-B1）

## 反模式与红线

- 🚫 收到「做一个 XX」直接开写代码，未确认目标用户与核心工作流（R4-B1）。
- 🚫 用户给 15 个功能的愿望单就全部照做（R4-B1）。
- 🚫 范围蔓延项默默照单全收，不告知代价与替代方案（R4-B2）。
- 🚫 第一版就引入支付/实时协作/通知中心/admin/i18n，无明确的验证触发条件（R4-B2）。
- 🚫 把「注册、仪表盘、通知、集成、支付『听起来有用』」当作进 MVP 的理由（R4-B1）。

## 交付前检查清单

- [ ] 已写下「一个目标用户 + 一个痛苦工作流 + 一个待验证假设」三句话并与用户确认
- [ ] 功能清单可逐项映射到 MVP 五件套之一；映射不上的进 backlog 并告知用户
- [ ] 核心 CRUD 只有「一个」，且能形成完整闭环（增删改查 + 分页）
- [ ] 澄清提问清单中与本次需求相关的问题都已问完并有答案
- [ ] 对已识别的范围蔓延项使用了拒绝话术，给出替代方案和触发条件
- [ ] 未向用户提供技术选型菜单，直接使用锁定栈

## 长尾不做（本 skill 域内）

支付订阅与多档定价、实时协作/WebSocket、通知中心与通知偏好设置、admin 后台 UI、i18n 多语言、SSO 第三方登录、A/B 测试与完整埋点体系——全部默认延后，待核心假设验证通过后由真实需求触发（R4-B2）。
